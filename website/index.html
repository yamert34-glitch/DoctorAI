01 THE DESIGN CHALLENGE

When Earth is
out of reach.

On Moon and Mars missions, communication delays or periods without contact may make immediate medical guidance difficult to access.

The project explores how health information could be gathered and organized onboard, between conversations with mission control.

01
EARTHCREW

Communication delays

Support from Earth may not be available in real time. Information gathered onboard needs to remain useful between contacts.

02
COMPUTELOCALPOWER · MEMORY · STORAGE

Limited onboard resources

Spacecraft hardware places constraints on compute, power, storage, and the software that can run within them.

03
INPUT?REVIEW

High-stakes uncertainty

Health information is complex, and the tools that organize it need clear limits and careful review.

02 THE APPROACH

A local-first
approach to
medical assistance.

Doctor AI is a C++ application that gathers structured symptom information, organizes health context, and can optionally use a locally running language model to draft a preliminary response.

Its configured assessment path can use local computation and local reference data without requiring cloud-based model inference.

04 HOW IT WORKS

A check-in, from
start to review.

A guided sequence keeps the interaction consistent and gives users a chance to review what they share.

01

PROFILE

Identify the user

A returning user can try face-template matching against a local profile. A new user can create one.

02

INTAKE

Collect health information

Structured questions cover symptoms, onset, patterns, other symptoms, heart rate, age, medications, and history.

03

PROCESSING

Organize the assessment

Phrase-based checks and local retrieval organize context. Experimental AI can be enabled to generate additional text.

04

REVIEW

Review the response

The response can appear on screen and, in configured environments, be read aloud.

05

LOCAL HISTORY

Retain local information

Assessment details can be saved to the selected local profile after the application's identity check.

07 OFFLINE-FIRST ENGINEERING

Designed around
the absence of
a connection.

Local processing reduces dependence on network access during the configured assessment path. It also puts model performance and device limits at the center of the engineering problem.

LOCAL PROCESSING

01

Local GGUF inference when experimental AI is enabled.

02

Local keyword-based lookup in the reference cache.

03

Local profiles and assessment storage.

04

No cloud inference is required by the configured assessment path.

ENGINEERING CONSTRAINTS

01

Model size and inference speed depend on device hardware.

02

Reference excerpts are limited to the sources collected in the local cache.

03

Spacecraft processor and radiation requirements are not demonstrated.

04

A separate cache-refresh utility can request public references over HTTPS.

ASSESSMENTLOCAL DEVICEMODEL + CACHE + PROFILEOPTIONAL NETWORK: REFERENCE REFRESH ONLY
08 PROJECT LIMITATIONS

Engineering responsibly
means knowing the limits.

Here’s what the current build can do, and where there’s room to grow.

01

AI response quality

Like other AI tools, generated answers can sometimes be wrong or miss important context, so they need human review.

02

Identity matching

Face-template matching can help select a profile, but it is not a full identity-verification system.

03

Local data protection

Assessment payloads use AES-256-GCM. Face templates and separately stored keys have different protections.

04

Hardware matters

Model speed, memory use, and reliability depend on the device. Spaceflight hardware has not been tested.

From prototype to

Ideas for where the project could go next, based on team priorities and testing.

CURRENT PROTOTYPE

What’s in the project

  • Structured symptom and health-history intake
  • Local C++ application architecture
  • Optional local language-model inference
  • Keyword-based local reference lookup
  • Touchscreen and configured voice interaction
  • Local profiles and limited payload encryption
  • Experimental pulse-sensor firmware

EXPERIMENTAL CAPABILITIES

What’s being explored

  • Preliminary text generated by local language models
  • Face-template matching for profile selection
  • Configurable local speech processing

FUTURE RESEARCH DIRECTIONS

Questions for next

  • Improve response consistency and output checks
  • Expand and evaluate reference material
  • Strengthen privacy and security protections
  • Systematic safety and usability evaluation
  • Performance on constrained hardware
  • Sensor integration and appropriate expert review

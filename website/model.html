04 MODEL DEVELOPMENT

Teaching a small model
to answer carefully.

Doctor AI runs a 0.5-billion-parameter Qwen model that we adapted ourselves. This page records what we trained it on, every model file we produced, and how each version scored on the same test suite.

01 HOW IT WAS FINE-TUNED

One base model,
a small adapter.

We started from the public Qwen2.5-0.5B-Instruct weights and trained a Low-Rank Adapter (LoRA) on top of them. The base weights stay frozen; only a small set of new parameters is learned.

Base model
Qwen2.5-0.5B-Instruct
0.49B parameters, public weights
Method
LoRA, rank 8
Alpha 16, dropout 0.05, on q_proj and v_proj
Trainable
540,672 params
About 0.1% of the model
Hardware
PyTorch MPS
Three epochs on an Apple Silicon Mac

What we trained it on

The data is synthetic. Each example is a chat-style record with an intake, a short reference excerpt, and an authored target answer. We wrote the targets to practise three things: one sentence of assessment, one sentence of evidence, and a citation that matches the excerpt that was actually supplied.

The excerpts come from 16 MedlinePlus respiratory summaries in our local reference cache. The examples deliberately include uncertain cases and evidence limits, not diagnoses or treatment instructions. They are not clinical labels, and the validation split is too small to prove generalization.

Why a 0.5B model

The target is a Raspberry Pi–class device, so memory and latency decide the model size. We also tested a much larger medical model: its file was about 2.49 GB and its mean response time was roughly 4.9× slower on the Mac. That is not a practical starting point for an onboard tool.

A 0.5B model is small enough to quantize under half a gigabyte, but it also makes mistakes a larger model would avoid. Most of the engineering on this page is about catching those mistakes rather than assuming they will not happen.

A one-case difference between the v2 files is noise, not a ranking.

04 WHAT WENT WRONG

Each version failed
differently.

A higher pass rate was not always a better model. These are the problems we actually found, in the order we found them.

  1. v1

    Fewer fallbacks, worse evidence.

    The first adapter cut format fallbacks from eight of eight to one of eight, which looked like a clear win. Reading the outputs showed otherwise: the wheezing case cited a chest-pain excerpt, and cough cases cited shortness-of-breath excerpts. The validator only checked that a citation ID existed in the supplied context; it never checked that the excerpt supported the sentence. On the current 102-case suite it is the weakest file we have: only 12 of 74 non-urgent cases produced a real assessment, against 33 for the untuned base model. Training on 24 examples made the model more likely to bail out or drift, not more accurate.

  2. v2

    Training on twelve examples taught caution, not grounding.

    The second adapter used a smaller, more cautious dataset. It reduced fallbacks again, but manual review still found a chest-pain citation on an upper-respiratory case, an acute-versus-chronic bronchitis mismatch, and one answer that only repeated the intake. Lower loss measured fit to our own examples, not medical correctness.

  3. Q4

    The filename said Q4_K_M. The tensors were not.

    The first v2 export was labelled Q4_K_M, but this model's attention head dimension (896) is not divisible by the block size the format needs, so the quantizer fell back for 144 of 290 tensors. Measured against the fp16 reference, that file was 4.5–4.7% off. Re-exporting the attention tensors at Q8_0 brought the error down to 0.56% — about eight times closer — for only a few megabytes.

  4. RAG

    “No chest pain” retrieved chest pain.

    The intake sentence “No difficulty breathing, chest pain, or high fever” was fed into reference retrieval word for word, so Chest Pain ranked as the top match for a mild congestion case. The fix strips negated spans from the retrieval query only; the prompt and the stored intake keep the original wording.

  5. Gate

    The validator was rejecting correct answers.

    The 0.5B model often wrote two assessment sentences and a second evidence paragraph. The format gate demanded exactly one of each, so correct, cited answers were replaced with “could not determine”. The application now keeps the cited sentence, drops the trailing paragraph, and still enforces the two-sentence shape. Format fallbacks on the suite went from four to zero.

  6. Scope

    Red flags were being thrown out as off-topic.

    The scope gate read the “not” inside “cannot” as a negation, so “Cannot stand because of chest pain” lost its red flag and was rejected as non-respiratory. “I cannot breathe” and “hoarseness” were missing from the vocabulary entirely. All three now route correctly.

05 LIMITS

What these numbers
do not mean.

The suite measures the behaviour of our software pipeline, not medical skill.

Not a clinical study

102 synthetic cases written by the team. No patients, no clinicians, no external validation set.

Rubric, not truth

A pass means the routing, format, citation, and safety rules held. It does not mean the assessment is medically correct.

Grounding is still weak

Even the best file named the expected condition in its evidence only about half the time. Citation validity is not entailment.

Mac measurements

All timings come from one Apple Silicon laptop. The Raspberry Pi build has not been benchmarked.
